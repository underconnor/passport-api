# Account administration and game activity

This extension keeps identity and activity in the existing PostgreSQL database. There is no public statistics API, raw student-number column, separate statistics database, or automatic public player ranking.

## Account list and erasure

`GET /v1/admin/members` is restricted to the configured admin origin, a current school session, and an enabled administrator. Parameters: `q` (trimmed, at most 128 characters), `membership=all|active|inactive|suspended`, `sort=name|newest|oldest`, `limit=1..50` (default 20), an optional `ids` comma-separated UUID list (1..50 distinct IDs, normalized to lowercase), and an opaque signed `cursor`. Cursors bind all query settings, including `ids` when present, and expire after 30 minutes. Empty, malformed, repeated or duplicate IDs are rejected with 400; missing/deleted/non-school IDs are simply absent. IDs intersect the existing search and membership filters, and omission preserves existing behavior. Selection UIs must retain unresolved saved IDs rather than silently removing them. The returned legacy `allowedServerIds` from the roster is informational; current admission is derived from server access modes and personal restrictions, and `eligibleServerIds` is the effective base scope. Search results and selected rows can be requested separately with `limit=10`; selecting a school user does not require active club membership. Results contain the existing member fields plus `revision`, `createdAt`, `administrator`, and nullable two-digit `admissionYear`, and `presence:{online,serverId,serverLabel,lastSeenAt}`; `total` and `nextCursor` accompany the list.

The unified query checks real name, Minecraft name, Discord ID/user/display name and legacy reference ID. An exact 8–10 digit query also checks the HMAC university key. Administrator member rows expose a nullable verified `studentId` after administrator-host, school-session and enabled-administrator checks; game responses still exclude full student numbers. After notice .5 consent and a fresh verified portal login, the number is retained as AES-256-GCM ciphertext for the authenticated owner profile and authorized administrator member list; HMAC matching remains unchanged. The school callback and the roster import use the same keyed HMAC to recognize the same student. A partial school-number search is intentionally unavailable.

`DELETE /v1/admin/members/:id` takes `{expectedRevision, confirmation}` where confirmation must equal the displayed name. It requires the same administrator checks plus same-origin CSRF. It rejects the caller's own account, the last owner even if viewer/operator accounts remain, stale revision, and mismatched confirmation. The operator helper `eraseSubject` uses a distinct `ops.subject_deleted` audit action when actor is null; it never creates or impersonates a web session.

Erasure deletes the Passport subject, sessions, consent, semester history, linking requests and all activity generations/counters. The source Google Sheet and roster HMAC record remain, so an eligible person can register again. A minimal Minecraft UUID/policy-version tombstone remains to reject old cached policies; its old name is erased and telemetry generation rotates. Discord jobs are projected to revoke roles and restore bot-owned nickname. The orphan contains no Discord name; its technical Discord ID and queue are deleted only after current-version acknowledgments confirm completion. Backup copies follow the existing encrypted retention period.

## Game policy and presence

`GET /v1/minecraft/policies/:uuid` adds `allowedServers:[{id,label,commandName}]`, `administrator:boolean`, `display.member`, nullable `display.admissionYear`, and `telemetry:{enabled,epoch,presenceEnabled,serverIds}`. Existing policy status/server authorization continues for people with older consent. Consent `2026-10-01.4` or the current `.5` is required before real name, member/year display, presence, or activity collection. Old `.3` remains sufficient for previously approved Discord synchronization. `POST /v1/me/privacy/consent {consent:{accepted:true,version}}` records the explicit updated consent and invalidates cached policy. A missing year remains null until a new verified school login supplies a valid four-digit admission-year prefix; there is no reversal of the HMAC.

`GET /v1/minecraft/players?query=...` returns up to 20 linked players matched by name, IGN, or exact UUID. Fields are `minecraftUuid`, `minecraftName`, `displayName`, `member`, `admissionYear`, `administrator`, `online`, `serverId`, `lastSeenAt`. It requires the private Minecraft service credential; player-facing administrative commands must also check the invoking player's fresh central administrator policy.

`POST /v1/minecraft/presence {serverId,observedAt,players:[uuid]}` accepts at most 500 distinct players. Observations may be at most 30 seconds old or 10 seconds ahead. Only linked, consented, currently permitted players are stored. The snapshot replaces that server's previous observations only when newer and expires after 90 seconds. Last-seen history is cleared after one day. This is server presence, not position tracking.

## Activity

`POST /v1/minecraft/stats/batches` accepts `{id,serverId,records}`. Every record contains `minecraftUuid`, `epoch`, and eight integer counters: `playSeconds`, `blocksBroken`, `blocksPlaced`, `damageTakenMilli`, `deaths`, `mobKills`, `playerKills`, `distanceCm`. A batch has 1–100 records with unique Minecraft UUIDs. Each delta must be between zero and 2,147,483,647. The last two are optional on input and default to zero for older Paper; all statistic responses include them. `distanceCm` is approximate movement from sampled vanilla statistic deltas, in centimetres; the API never receives coordinates or movement events. Migration `20261002000200_activity_distance` adds zero-default nonnegative bigint columns and does not fabricate historic values. Damage is in thousandths of one Minecraft health point; two health points are one heart.

Batch IDs are UUIDs. Plugins must save the exact batch before sending and retry that ID/payload after timeouts. The API returns `{accepted:true,duplicate,received,ignored}`. A changed payload under the same ID conflicts. Six-counter digests already stored before rollout remain valid for retries whose new counters are both zero; an old batch cannot be reused to append movement or player kills. Validation, counters, receipt, deletion and policy changes use one database transaction with the common writer lock. Unlinked, old-generation, unconsented or no-longer-permitted records are ignored permanently. An unlink/relink or deletion rotates the telemetry epoch, so replaying an old saved batch cannot recreate erased account data. Idempotency receipts retain only a random batch ID, payload digest and aggregate counts; they retain no raw activity record.

`GET /v1/me/stats` returns only the signed-in person's counters. `GET /v1/admin/stats` returns the overall counters and `playerCount` and `onlinePlayerCount`. `GET /v1/admin/members/:id/stats` requires an administrator. `GET /v1/minecraft/players/:uuid/stats` requires the private service credential. All responses use `{available:true,totals,servers:[{serverId,label,...counters,onlinePlayerCount}]}`. Own/member responses include `presence:{online,serverId,serverLabel,lastSeenAt}`. Overall online counts count current consented presence observations; each allowed server row is present even before its first activity counter arrives. Owner responses suppress inaccessible server rows and their counters from combined totals. Collection-disabled servers are absent from statistics server rows and selectors; their preserved history is excluded from all regular aggregates, including administrator totals/player counts. Counters are JSON safe integers, with internal PostgreSQL bigint storage and explicit overflow rejection. The database starts empty; old gameplay is not fabricated or backfilled.

## Owner identity and semester validity

`GET /v1/me` includes `studentId:string|null` (8–10 digits). A new verified portal login with `.5` consent stores the number; an old profile or admin-only login remains null. Renewal alone cannot recover an HMAC. Only the owner profile, authorized administrator member list and administrator statistics export return full numbers. Ciphertext is never returned; Minecraft/Discord service DTOs and audits contain neither full numbers nor ciphertext. Subject deletion removes its ciphertext. See [school-identity.md](school-identity.md) for migration and expiry rules.

Administrative roles and invitation/session revocation are specified in [operator-management.md](operator-management.md).

The Paper sampler sums vanilla walking, sprinting, crouching, swimming, water/underwater walking, climbing, flying, elytra, minecart, boat, pig, horse, strider, happy-ghast and nautilus centimetre statistics. Falling is excluded to avoid double counting with air movement. It uses the existing one-second main-thread timer plus final samples, and resets baselines on session/epoch changes or decreased counters. Privacy notice .5 now names player kills and approximate distance; existing consent versions and receipts are not rewritten or forcibly renewed.

## Collection settings and administrator resets

Personal collection controls have been removed. `GET` and `PUT /v1/me/statistics-settings` return 404. Only administrator server settings control collection; an old `Subject.statisticsEnabled=false` value is ignored by current policy/ingest logic. Migration `20261002020000_statistics_export_manual` normalizes old preferences to true and rotates affected Minecraft epochs. Consent remains mandatory and is never created or restored by this migration. Presence and real-name display remain separately consent/authorization gated. Paper collects only when `telemetry.enabled` is true, its configured server is in `telemetry.serverIds`, and the lease is valid.

Administrator server DTOs and PUT settings add `statisticsEnabled` (omission preserves the old setting). Migration `20261002010000_statistics_controls` keeps current user preferences enabled, sets the existing production `ssu_lobby` to collection-disabled, and never deletes history. Seed/heartbeat creation also disables that exact production lobby by default. Later heartbeats preserve the administrator setting. Other server defaults remain enabled, still requiring real consent and game authorization.

Stats responses add `collection:{enabled,effective,managedBy:"administrator",consentGranted,excludedServerIds,historyRetained:true}`; enabled/effective/consentGranted are null for the overall administrator view. There is no personal collection switch. A server off excludes that server from normal totals and player counts; re-enabling restores its preserved totals. Presence counts are independent of counters. Inaccessible server names/IDs and counters are absent from owner responses.

`POST /v1/admin/stats/reset/preview` takes exactly `{scope:"subject",subjectId}`, `{scope:"server",serverId}`, or `{scope:"all"}`. It returns that scope, `affectedSubjects`, `rows`, all eight `totals`, `expectedRevision`, and `confirmation:"통계 초기화"`. `POST /v1/admin/stats/reset` takes the same scope plus expectedRevision/confirmation. Both require a writable administrator and same-origin CSRF; viewer and service credentials cannot reset. A target administrator's counters require an owner. There is no user reset endpoint. No deployment resets real counters.

The reset revision binds actor, scope, target generations and current epochs, plus previous resets. Counter increments within existing generations do not invalidate the preview; execution clears selected records through its transaction commit. New target generations/changed epochs/another reset cause `statistics_reset_changed` and require another preview. The preview has no separate wall-clock expiry. Scope is bounded to 5,000 affected subjects and 50,000 rows (`statistics_reset_too_large`). All scopes include excluded-server historical rows where selected. Server settings, account data, consent and immutable batch receipts remain intact. Daily buckets within the selected scope are deleted in the same reset transaction.

Server collection changes and server/all resets rotate every linked identity epoch. Queued records that have not yet been committed may be excluded, including records from other servers; records already committed to the database outside the selected reset scope are preserved. The backlog duration is not bounded: the statistics endpoint can remain unavailable while policy requests still succeed. This explicit tradeoff prevents old offline batches from reviving erased counters or crossing off/on boundaries. Data deletion, epoch rotation, policy events and the audit record share the policy writer transaction. Retried original batch IDs remain deduplicated; unknown old IDs are permanently ignored by epoch checks.

Deployment order: API migration/code, then web/admin. Current Paper already honors administrator server collection policy. Do not roll back to code that permits personal opt-out or ignores daily resets/reset epochs; retain a compatible image.

## Collection dates and period views

Owner, global administrator and member statistics endpoints accept optional paired `from=YYYY-MM-DD&to=YYYY-MM-DD`, inclusive Korean calendar dates, at most 366 days. Without dates, counters remain cumulative. With dates, counters aggregate new `ActivityDaily` buckets only. Buckets begin at `StatisticsHistory.availableFrom`, set by the migration; legacy cumulative data is preserved but never assigned invented dates. A delayed offline batch belongs to the Korean date when the API receives it, not an assumed gameplay date. Duplicate receipts do not increment either store.

Responses include `period:{from,to,availableFrom,timezone:"Asia/Seoul",basis:"receivedAt"}` and `daily:[{date,serverId,...eightCounters}]`. The default cumulative response includes only the latest 30 days of daily points; explicit periods bound all daily points. Root and server rows add `firstCollectedAt`/`lastCollectedAt` ISO timestamps or null. These describe collection observed since this migration, not a user's first-ever login. Empty dates are omitted. Both server authorization and collection settings filter daily and cumulative views identically. Reset and subject erasure remove daily data as well as cumulative data.

## Administrator Excel export

`POST /v1/admin/stats/export` accepts `{serverId?,subjectId?,from?,to?}` and returns `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, filename `passport-statistics.xlsx`, `Cache-Control: private, no-store`. A current school-authenticated owner/operator session, correct administrator host, and CSRF are required; viewers, ordinary users and service credentials cannot download. Export rechecks permissions under the policy writer lock and records a metadata-only audit event.

The workbook contains one row per subject and collection-enabled server: Passport user ID, full verified student number, real name, Minecraft UUID/IGN, Discord ID, server ID/name, eight metrics, and first/latest collection timestamps. A subject without recorded activity has zero metrics; missing verified student numbers remain blank. Identifiers and all user text are explicit OOXML inline strings, never formulas, so full Discord IDs and formula-looking names cannot lose precision or execute. Units are seconds, HP and metres. A second sheet records scope, period coverage and receipt-date semantics. Exports are bounded to 5,000 subjects and 50,000 source/output rows; narrower filters are required beyond that. At most two exports run concurrently per API process; another receives HTTP 409 `statistics_export_busy` and can retry after an active download finishes. Slots release on success or error. No temporary plaintext workbook is stored on the server.

Workbook package follows [Microsoft SpreadsheetML structure](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/structure-of-a-spreadsheetml-document); archive generation uses [fflate](https://github.com/101arrowz/fflate).

## Administrator membership filter

`GET /v1/admin/stats` and the JSON body of `POST /v1/admin/stats/export` accept `membership: all | active` (default `all`). Active means the current subject is a u-SAINT identity with active membership, an unexpired `verifiedUntil` at the shared query instant, and no access suspension, matching the administrator member list. The same cohort filters all eight counters, server totals, distinct historical players, daily buckets, first/last collection timestamps, and current presence. Period queries select the current cohort; they do not reconstruct historical membership. Presence keeps its existing server scope independently of collection settings, while statistics-disabled servers remain excluded from counters, server rows and workbooks. The global `period.availableFrom` rollout timestamp is unchanged.

Personal/member statistics reject this query field; the private Minecraft endpoint retains its existing ignored-query behavior. Reset inputs are unchanged. Export intersects membership with period, server and subject filters, includes zero-counter rows for matching subjects, and returns a header-only sheet when no subjects match. An existing nonmember subject combined with `active` returns an empty workbook; an unknown subject still returns 404. Workbook metadata records cohort, current-membership basis and UTC evaluation time. Export audit records membership, including the default `all`, without raw identity values. No migration or collection-setting change is needed.
